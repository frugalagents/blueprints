The Smart Developer's Token Playbook

How to get more out of a coding agent by shaping the system around it — not by remembering to be careful

There's a pattern every heavy coding-agent user knows. A session starts sharp. The agent is fast, the edits are surgical, the context is tight. Then, twenty or thirty minutes in, it starts to drift. It re-reads files it already has. It reasons in circles. A single test run quietly costs 5,000 tokens. By the time you notice, you've burned through your daily budget on work that should have cost a tenth as much.

The instinct is to blame discipline — I should have /clear'd sooner, I should have written a tighter prompt. But that's the wrong lesson. A developer doesn't get more effective by remembering to be careful. They get more effective by shaping the system so carefulness is the default.

That's what this playbook is about. Not prompt tricks. The harness.

The organizing idea is simple and it holds up across every coding agent on the market:

Governance catches ~60% of waste automatically. Trained habits refine the last ~40%. A disciplined workflow keeps both from being wasted on the wrong work. And most of it can itself be automated — so the developer inherits the playbook on git clone.

We'll use Claude Code as the worked example because its configuration surface is the most explicit, but the framework maps cleanly onto any agentic coding tool — Kiro, Copilot, Cursor, Gemini CLI. The names of the config files change; the tiers don't.

Here's the framework we'll build:

Part 1 — Understand the Machine

You can't optimize what you don't understand. Before any hook or budget, a smart developer needs an accurate mental model of what actually consumes tokens — and where the levers live.

The harness is the product

When you use a coding agent, you're not talking to a model. You're talking to a harness that wraps the model: it assembles the system prompt, injects tool schemas, manages the context window, decides what files to read, and shuttles every tool result back into the conversation. The model is stateless. The harness is where all the token economics happen.

The configuration hierarchy

Claude Code — like most mature agents — resolves configuration in a cascade. Understanding this cascade is what lets you decide what to set where: broad policy at the top, personal ergonomics in the middle, project truth at the bottom.

The configurable surface at each level is the same handful of primitives:

Primitive What it does Token relevance
CLAUDE.md Persistent instructions injected every turn High — every wasted line is billed on every request
MCP servers External tool providers High — each server's schemas inflate the system prompt continuously
Skills / commands Reusable, invocable procedures Medium — replace verbose re-prompting
Hooks Shell scripts that fire on lifecycle events Enforcement — the automation backbone (Part 6)
Plugins Bundled packs of the above Distribution — ship the whole playbook at once

Hold this model in your head. Everything below is just applying leverage at the right point in this cascade — starting at the top, where a single decision covers everyone.

Part 2 — Tier 1: Governance (the automatic 60%)

Governance is what you set once so no developer has to remember anything. It's enforced centrally, lives in version control, and re-converges every time someone clones the repo. If a rule only works when a tired engineer remembers it at 5pm on a Friday, it isn't governance — it's a wish. This tier does the majority of the work precisely because it removes human memory from the loop.

The mental model: four controls, stacked from "cheapest to set" to "highest ongoing leverage."

2.1 CLAUDE.md discipline — and the 42K-token trap

CLAUDE.md is the highest-leverage file in the system because it's injected into every single turn — and for the same reason it's the most common source of silent waste. The failure mode is well-documented: one engineer's CLAUDE.md grew to 42,000 tokens because every painful debugging session added "just one more rule." At Claude Sonnet input pricing (~~$3/M tokens), a 42K-token file that rides along on a 200-turn day silently burns ~~$25/developer/day in context tax alone — before a single useful token is generated. Multiply by a 50-person team and the bloated instruction file alone is a five-figure annual line item.

The discipline is three rules:

  • Budget it. Treat CLAUDE.md like carry-on with a hard weight limit — 1–2K tokens, not 40K. If it doesn't change agent behavior, it's a comment, not context.
  • Import, don't inline. Reference detail with @path/to/detail.md; those files load only when the task actually touches them. This is the single biggest win — it converts always-on tokens into on-demand tokens.
  • Layer it. CLAUDE.md resolves hierarchically — a lean root file for repo-wide truth, plus per-directory CLAUDE.md files that load only when the agent works in that subtree. A monorepo's services/payments/CLAUDE.md shouldn't tax work happening in web/.
# CLAUDE.md — keep this file under ~1,500 tokens

## Project
Payments service. Python 3.12, FastAPI, Postgres. Tests: `pytest -q`.

## Response style
- Be terse. No preamble, no "Here's what I'll do" — just do it.
- Show diffs, not whole files, unless asked.
- Ask before installing dependencies.

## Conventions (details imported on demand)
- Code style: @docs/style.md
- DB migration workflow: @docs/migrations.md
- Security rules: @docs/security.md

## Guardrails
- Never write to `main` directly. Never touch `infra/` or `.env`.
- Prefer running `rg`/`grep` over reading whole files into context.

The audit habit: run a token count on CLAUDE.md in CI and fail the build if it crosses a ceiling (say 2K). The file that never gets audited is the file that hits 42K.

2.2 Model routing as policy

Most production traffic never needed a frontier model. Linting, formatting, renaming, commit messages, simple edits — these are fast-model work. The economics are stark: a frontier reasoning model can cost 15–30× per token what a fast model costs, yet studies of real coding-agent traffic find ~70% of turns are low-reasoning. Paying Opus prices for a rename is the purest form of the token tax.

Make the tier a policy, not a per-developer choice:

// .claude/settings.json — routing policy fragment
{
  "model": {
    "default": "sonnet",
    "routing": [
      { "match": ["lint", "format", "rename", "commit message", "typo"],
        "model": "haiku" },
      { "match": ["architecture", "debug", "design", "security review"],
        "model": "opus" }
    ]
  }
}

The principle is vendor-neutral: a three-tier stack (fast / balanced / power), cheapest capable model as default, explicit escalation for hard work. Teams that tune this report 40–85% cost reduction with no visible quality drop — because the frontier model was never the thing making most turns good.

2.3 Budgets, caps, and alerts

Token budgets turn an invisible, unbounded cost into a bounded, observable one. This matters more than it sounds: AI spend can swing 300% month-over-month on a single feature launch, and the horror stories are real — one enterprise rolled coding agents to ~5,000 engineers and burned its entire annual AI budget by April at $500–2,000/engineer/month. Budgets are the circuit breaker.

// .claude/settings.json — budget fragment
{
  "budget": {
    "perSessionTokens": 400000,
    "perUserDailyTokens": 3000000,
    "alertThresholds": [0.5, 0.8, 1.0],
    "onExceed": "block"
  }
}

Set hard ceilings, alert at 50/80/100%, and decide the onExceed behavior deliberately — block for cost-sensitive orgs, warn where velocity matters more. The point isn't to ration; it's to make overruns visible before the invoice, not after.

2.4 The context baseline — .claudeignore + env vars

Two set-and-forget controls quietly lower the floor for everyone:

  • .claudeignore — exclude build dirs, lockfiles, vendored code, and generated artifacts from indexing. The agent can't waste tokens reading node_modules/ if it never sees it.
  • Autocompact + thinking budget env vars — compact the context automatically before it's overflowing (not at the last second), and cap extended-thinking spend per turn:
"env": {
  "CLAUDE_AUTOCOMPACT_PCT_OVERRIDE": "70",  // compact at 70% full, not the default
  "MAX_THINKING_TOKENS": "8000"             // cap reasoning spend per turn
}

2.5 Hooks — enforcement that fires itself

This is the heart of Tier 1. Hooks are shell scripts the agent runs automatically at lifecycle events. They convert "please remember to…" into "the system won't let you not." Full working code is in Part 6 — here's the mental model:

  • PreToolUse — inspect and block an action before it runs (protect branches, reject dangerous shell commands).
  • PostToolUse — react after an action (auto-lint, count tokens, reject oversized diffs that signal a hallucinated rewrite).
  • Notification — fire an external alert (Slack webhook on cost threshold).

The power of hooks is that they're deterministic — they don't depend on the model choosing to behave, or a developer choosing to remember. Write once, fires on every action, for every developer, forever.

Governance has now done the automatic 60%. What it can't do is exercise judgment inside a live session — that's where trained habits take over.

Part 3 — Tier 2: Smart-Developer Habits (the daily 40%)

Governance sets the floor. Habits are what a developer does in-session to refine the last stretch — the part that genuinely needs judgment about this task, right now. Here's the pattern every heavy user recognizes: a session starts sharp and dies 20–30 minutes in. The agent begins re-reading files it already has, reasoning in circles, and a single cargo test or pytest run quietly costs ~5,000 tokens. Habits are what keep a session sharp past that wall.

The good news: adopting the full habit stack cuts typical session token usage by 60–80% in practitioners' own measurements — and most of it is muscle memory, not effort.

3.1 Session hygiene — the highest-ROI habit

Stale context is the #1 source of session bleed, because everything in context is re-billed on every subsequent turn. Carrying your morning's bug fix into your afternoon's feature means paying for those tokens hundreds of times.

  • /clear between unrelated tasks. The cheapest habit and the biggest win. New task = clean context.
  • Proactive /compact at breakpoints. Don't wait for auto-compact to fire mid-thought at the worst moment. Compact deliberately — after a milestone, before a new subtask.
  • /done to close. Explicitly end a session so idle follow-ups don't silently accumulate context you're still paying to carry.

3.2 The standard slash-command pack

Slash commands turn a paragraph of instruction into a keystroke — and, crucially, into a team standard everyone shares. Ship these committed to .claude/commands/ (Part 6 auto-installs them):

# .claude/commands/cheap.md
Switch to the fast/small model for the next several turns.
Use for lint, format, rename, and other low-reasoning tasks.


# .claude/commands/scope.md
Drop all context except the files relevant to the current task:
$ARGUMENTS
Re-anchor on those files only. Summarize what you're keeping.


# .claude/commands/review.md
Spawn a subagent on the cheap model to review the current diff.
Report only Critical and Major issues. Do not self-review on the power model.

Round it out with /budget (remaining tokens), /compact, and /done. The win is consistency: when /scope means the same thing for everyone, context discipline stops being a personal quirk and becomes a shared reflex.

3.3 In-session tactics

  • Plan Mode first. On any non-trivial task, make the agent produce a plan before it touches code. A plan is a few hundred tokens; a wrong implementation you have to unwind is tens of thousands. This is the in-session cousin of the spec-driven workflow in Part 4.
  • rg/grep over whole-file reads. Searching for the relevant 20 lines beats pulling 2,000 into context. Put this in CLAUDE.md so it's the default, not a choice.
  • Tighter prompts. State the outcome and the constraints; skip the backstory. Verbose prompts cost tokens on the way in and bias the model toward verbose output on the way out.
  • Answer in the terminal, not the context. Prefer git log, ls, cat file | head run as commands over asking the agent to "load and summarize" — bash output is transient; loaded files are sticky.

3.4 Subagent discipline

Subagents are a double-edged habit: they isolate work (good — a reviewer subagent doesn't pollute your main context) but can multiply cost (bad — an agent spawning agents spawning agents). The rules:

  • Force subagents to the cheap tier unless the sub-task genuinely needs power (e.g. /review runs on Haiku-class, not Opus).
  • Cap depth — no recursive spawning. One level of delegation, not a tree.
  • Use them to protect the main thread — offload a noisy search or a diff review to a subagent so the main session's context stays clean.

3.5 MCP discipline

MCP servers are powerful and quietly expensive: every connected server's tool schemas are injected into context on every turn. Five servers × ten tools each can dominate your system prompt before you type a word — a fixed tax on every single request of the session.

  • Connect only what this project needs. An unused MCP server is pure overhead.
  • Convert hot MCP tools into local slash commands. You keep the capability and shed the per-turn schema cost — one of the highest-leverage moves for MCP-heavy setups.
  • Cache schemas; don't re-fetch each session.

Governance and habits make each turn cheaper. But the biggest waste isn't an expensive turn — it's building the wrong thing and redoing it. That's what workflow fixes.

Part 4 — Tier 3: Workflow (the multiplier)

The first two tiers make each turn cheaper. Workflow makes the whole task cheaper — by getting it right the first time. The highest-leverage move here has a name and, as of 2026, a real toolchain: spec-driven development (SDD).

The shift is from vibe coding — prompt, generate, iterate by feel — to an explicit chain: discovery → spec → plan → tasks → code, where a versioned spec is the source of truth the agent derives code from. Karpathy, who coined "vibe coding," now calls the professional version agentic engineering: "you are not writing the code 99% of the time, you are orchestrating agents who do, and acting as oversight."

4.1 Why workflow is a token lever, not just a quality one

Rework is the most expensive thing an agent does. A vague prompt produces almost-right code, which triggers rounds of re-reading, re-reasoning, and re-editing — each billed. A spec front-loads the thinking (cheap) so implementation lands in one pass and skips the expensive middle.

The signal is concrete: independent MIT/Microsoft/GitHub research documents up to 56% less programming time with structured AI workflows; early adopters report 3–10× higher first-pass success on non-trivial tasks. A real worked example (below) went from "want CSV export" to merged in ~90 minutes — vs ~90 min of generation plus 45 min of unwinding without a spec. The spec isn't faster on the first pass; it's faster on the rework pass.

4.2 When a workflow actually makes sense

This is the part most guides skip. A spec has real upfront cost — don't pay it when the task doesn't need it. The rule of thumb:

If you'd write a PR description longer than three paragraphs, write a spec. If it's a Tuesday-afternoon prototype, don't.

The two aren't rivals — they're different tools for different moments. The trap isn't vibe coding; it's letting a Tuesday-afternoon prototype quietly become a production feature without anyone stopping to write down what it's supposed to do.

4.3 The practical setup — Spec Kit + Claude Code

You don't need a dedicated tool to start — a markdown spec the agent reads before implementing is SDD in its simplest form. But the most-deployed toolchain is GitHub Spec Kit, which installs a pipeline of slash commands into your agent. Install it and you get nine commands; the core flow uses a subset, in order:

# One-time: scaffold Spec Kit into the repo (registers slash commands)
specify init            # or install the Claude Code Spec Kit plugin

# Per feature — run these in order inside Claude Code:
/constitution   # (once per project) establish enduring principles
/specify        # brief → requirements.md  (user stories + acceptance criteria)
/clarify        # force-resolve ambiguities the spec missed  ← most-skipped, highest-value
/plan           # requirements → design.md  (architecture, schema, contracts)
/tasks          # design → tasks.md  (ordered, dependency-aware, parallel markers)
/implement      # walk the task list, one diff at a time

Each phase emits a markdown artifact the next consumes — requirements.md → design.md → tasks.md — all committed to git next to your code. The discipline: every line of code traces to a task, every task to a design decision, every decision to a requirement.

Spec vs CLAUDE.md — don't confuse them: CLAUDE.md describes how your codebase works (standing conventions every change conforms to). A spec describes what one specific change does. In the source author's phrase: CLAUDE.md is the constitution; specs are the bills.

4.4 Skills as workflow building blocks

Yes — skills are a first-class part of the workflow, at two levels:

  1. The workflow steps themselves are skills. /specify, /clarify, /plan, /tasks, /implement are packaged, invocable procedures — Spec Kit ships them as a command/skill pack. The workflow is a chain of skills.
  2. Tasks invoke domain skills. Once /tasks emits T1–T7, each task can call a reusable team skill — a db-migration skill, an api-endpoint skill, a test-writer skill. The spec decides what; skills encode the how your team does it consistently.
Primitive Role in the workflow
Spec What to build — the contract
Skills Reusable how — invoked by workflow steps and by generated tasks
Hooks Enforcement wrapped around every step (Part 6)
CLAUDE.md Standing conventions the spec and skills conform to

Skills are the connective tissue: a workflow is a chain of skills, and the tasks it generates fire more skills. Chaining specialized skills into a pipeline (e.g. prd → scaffold → build → review) is how a one-off workflow becomes a repeatable, org-shared asset.

4.5 A worked example — rate-limited CSV export

Concrete beats abstract. /specify Export dashboard data as CSV with rate limiting produces requirements.md:

US-1: Authenticated user exports current dashboard view as CSV
  Given a user is authenticated and viewing a dashboard
  When they click "Export CSV"
  Then a CSV of the visible rows downloads, named <dashboard>-<date>.csv
  And the user is rate-limited to 10 exports/hour/account
US-2: Large dataset export streams progressively ...

/plan turns that into design.md:

## Architecture
- Endpoint: POST /api/dashboards/:id/export (server-only)
- Auth: required, scoped to dashboard owner
- Rate limit: Redis-backed, 10/hour/account, 429 + Retry-After
- CSV: streamed via Node readable stream; 100MB cap → 413
- Audit: log user_id, dashboard_id, timestamp, row_count

/tasks decomposes into a dependency-ordered list:

- [ ] T1: Redis rate-limit middleware            [parallel-safe]
- [ ] T2: Audit-log table migration              [parallel-safe]
- [ ] T3: POST /export endpoint                  [depends: T1, T2]
- [ ] T4: Streaming CSV generator                [parallel-safe]
- [ ] T5: Wire endpoint → generator              [depends: T3, T4]
- [ ] T6: Export CSV button in UI                [depends: T5]
- [ ] T7: 429 / 413 error handling in UI         [depends: T6]

/implement then produces the code one task at a time. Notice the rate limit, streaming, and audit log — the exact things a bare "add a CSV export button" prompt silently omits and you'd discover in production.

4.6 Toolchain — pick your weight

Spec Kit isn't the only option; they're not interchangeable:

Tool Shape Pick it when
GitHub Spec Kit CLI, agent-agnostic, markdown-first Default starting point; taskstoissues pushes tasks to GitHub Issues
Kiro AWS agentic IDE, same requirements/design/tasks phases You're in AWS-heavy territory and want an opinionated IDE
OpenSpec Lightest — propose / apply / archive, pure git markdown You want minimal touch, no IDE or cloud dependency
Tessl Spec-as-typed-data the tool reasons over You want maximum spec-as-data leverage and accept lock-in

Wiring it back to the playbook: specs live in git beside .claude/, a good spec is the ultimate /scope (context stays tight from turn one), and the bootstrap installer in Part 6 can scaffold the spec commands so a cloned repo is workflow-ready on day one.

That's the full framework. The rest is execution: the checklists to adopt it, the code to automate it, and the sequence to roll it out.

Part 5 — The Playbook (the checklists)

Everything above, distilled into three checklists a team can adopt tomorrow.

One-time setup (baseline reduction — do once per repo)

  • [ ] .claudeignore excluding build dirs, lockfiles, vendored code
  • [ ] Model routing policy (fast default, explicit escalation)

  • [ ] Hook suite installed (PreToolUse, PostToolUse, Notification)
  • [ ] Standard slash-command pack committed to .claude/commands/
  • [ ] Autocompact + thinking-token env baseline set

Daily habits (per session)

  • [ ] /clear when switching tasks
  • [ ] Plan Mode before non-trivial work
  • [ ] /cheap for low-reasoning turns
  • [ ] Proactive /compact at breakpoints
  • [ ] rg/grep over whole-file reads
  • [ ] /budget check-in on long sessions
  • [ ] /done to close

New-project kickoff

  • [ ] Run the bootstrap installer (Part 6)
  • [ ] Generate CLAUDE.md from a repo scan
  • [ ] Write the first spec before any code
  • [ ] Confirm routing + budgets inherited from org policy

Combined, teams consistently report 60–80% token reduction from adopting the full stack — most of it structural, not willpower.

Part 6 — Automate the Playbook: The Self-Configuring Repo

Here's the thesis that ties it together: the developer should not have to remember any of this. The playbook ships as installable artifacts. On git clone, the repo configures itself. What follows is full, working code — not sketches.

6.1 The bootstrap installer

One idempotent script writes the entire .claude/ configuration. Run it locally or in CI so every repo re-converges to policy.

#!/usr/bin/env bash
# setup-claude-code.sh — bootstrap a repo with the token playbook.
# Idempotent: safe to run repeatedly. Usage: bash setup-claude-code.sh
set -euo pipefail

ROOT="$(git rev-parse --show-toplevel 2>/dev/null || pwd)"
CLAUDE_DIR="$ROOT/.claude"
HOOK_DIR="$CLAUDE_DIR/hooks"
CMD_DIR="$CLAUDE_DIR/commands"

mkdir -p "$HOOK_DIR" "$CMD_DIR"

echo "→ Writing settings.json (routing, budgets, hooks)…"
cat > "$CLAUDE_DIR/settings.json" <<'JSON'
{
  "model": {
    "default": "sonnet",
    "routing": [
      { "match": ["lint","format","rename","commit message","typo"], "model": "haiku" },
      { "match": ["architecture","debug","design","security review"], "model": "opus" }
    ]
  },
  "budget": {
    "perSessionTokens": 400000,
    "perUserDailyTokens": 3000000,
    "alertThresholds": [0.5, 0.8, 1.0],
    "onExceed": "block"
  },
  "env": {
    "CLAUDE_AUTOCOMPACT_PCT_OVERRIDE": "70",
    "MAX_THINKING_TOKENS": "8000"
  },
  "hooks": {
    "PreToolUse":  [{ "matcher": "Bash|Write|Edit", "hooks": [{ "type": "command", "command": ".claude/hooks/pre_tool_use.sh" }] }],
    "PostToolUse": [{ "matcher": "Write|Edit",       "hooks": [{ "type": "command", "command": ".claude/hooks/post_tool_use.sh" }] }],
    "Notification":[{ "matcher": "*",                "hooks": [{ "type": "command", "command": ".claude/hooks/notify.sh" }] }]
  }
}
JSON

echo "→ Writing hook scripts…"
# (hooks written in 6.2 below)
bash "$ROOT/.claude/_write_hooks.sh" 2>/dev/null || true

echo "→ Writing standard command pack…"
cat > "$CMD_DIR/cheap.md"  <<'MD'
Switch to the fast/small model for the next several turns (lint, format, rename).
MD
cat > "$CMD_DIR/scope.md"  <<'MD'
Drop all context except files relevant to: $ARGUMENTS
Re-anchor on those only; summarize what you kept.
MD
cat > "$CMD_DIR/review.md" <<'MD'
Spawn a subagent on the cheap model to review the current diff.
Report only Critical and Major issues.
MD

echo "→ Installing git pre-commit convergence check…"
HOOK="$ROOT/.git/hooks/pre-commit"
cat > "$HOOK" <<'SH'
#!/usr/bin/env bash
# Re-assert policy on every commit.
[ -f .claude/settings.json ] || { echo "Missing .claude/settings.json — run setup-claude-code.sh"; exit 1; }
SH
chmod +x "$HOOK"

echo "✓ Playbook installed. Commit .claude/ to share it with the team."

6.2 Hooks — the full enforcement suite

PreToolUse — block dangerous actions before they run. The agent passes the pending tool call as JSON on stdin; exit code 2 blocks it.

#!/usr/bin/env bash
# .claude/hooks/pre_tool_use.sh — veto risky actions. Exit 2 = block.
set -euo pipefail
payload="$(cat)"                      # JSON describing the pending tool call
tool="$(jq -r '.tool_name' <<<"$payload")"
cmd="$(jq -r '.tool_input.command // empty' <<<"$payload")"
path="$(jq -r '.tool_input.file_path // empty' <<<"$payload")"

# 1) Protect sensitive paths from writes/edits
case "$path" in
  *".env"*|*"/infra/"*|*"secrets"*)
    echo "BLOCKED: writes to $path are not allowed by policy." >&2; exit 2;;
esac

# 2) Reject dangerous shell commands
if [[ -n "$cmd" ]]; then
  if grep -Eq '(rm -rf /| rm -rf \*|curl [^|]*\| *(ba)?sh|:\(\)\{)' <<<"$cmd"; then
    echo "BLOCKED: dangerous shell pattern in: $cmd" >&2; exit 2
  fi
fi

# 3) Never let the agent commit straight to main
if grep -Eq 'git (commit|push).*(origin/)?main' <<<"$cmd"; then
  echo "BLOCKED: direct commits/pushes to main are forbidden. Use a branch." >&2; exit 2
fi
exit 0

PostToolUse — react after a file write: auto-lint, count tokens against budget, reject hallucinated mega-diffs.

#!/usr/bin/env bash
# .claude/hooks/post_tool_use.sh — lint, budget-count, reject huge diffs.
set -euo pipefail
payload="$(cat)"
path="$(jq -r '.tool_input.file_path // empty' <<<"$payload")"

# 1) Reject oversized single-file diffs (sign of a hallucinated rewrite)
if [[ -n "$path" && -f "$path" ]]; then
  added="$(git diff --numstat -- "$path" 2>/dev/null | awk '{print $1}')"
  if [[ -n "${added:-}" && "$added" -gt 500 ]]; then
    echo "WARNING: $path changed $added lines (>500). Review before continuing." >&2
  fi
  # 2) Auto-lint on write (language-detected)
  case "$path" in
    *.py) ruff check --fix "$path" >/dev/null 2>&1 || true ;;
    *.js|*.ts) npx --no-install eslint --fix "$path" >/dev/null 2>&1 || true ;;
  esac
fi

# 3) Cumulative token ledger (simple append-and-sum)
tokens="$(jq -r '.usage.total_tokens // 0' <<<"$payload")"
ledger=".claude/.token_ledger"; echo "$tokens" >> "$ledger"
sum="$(awk '{s+=$1} END{print s}' "$ledger")"
cap=400000
if (( sum > cap )); then
  echo "BUDGET EXCEEDED: session used $sum tokens (cap $cap). Consider /clear." >&2
fi
exit 0

Notification — push a Slack alert when spend crosses a threshold.

#!/usr/bin/env bash
# .claude/hooks/notify.sh — alert on cost threshold. Needs $SLACK_WEBHOOK_URL.
set -euo pipefail
msg="$(jq -r '.message // "Claude Code notification"' <<<"$(cat)")"
[[ -z "${SLACK_WEBHOOK_URL:-}" ]] && exit 0
curl -s -X POST -H 'Content-type: application/json' \
  --data "{\"text\":\":robot_face: $msg\"}" "$SLACK_WEBHOOK_URL" >/dev/null || true
exit 0

6.3 CLAUDE.md generator — a meta-agent, not a template

Don't hand-write CLAUDE.md and don't ship a generic template. Generate a lean one from a repo scan, and regenerate it when dependencies change. This is a slash command you run once per project:

# .claude/commands/gen-claude-md.md
You are generating a LEAN CLAUDE.md for this repository.

Steps:
1. Detect the stack: read package.json / pyproject.toml / go.mod / Cargo.toml.
2. Find the test command, lint command, and build command.
3. Infer directory conventions from the top two levels of the tree.
4. Detect the primary language's idioms.

Output rules (HARD CONSTRAINTS):
- Total file MUST be under 1,500 tokens. Count and report the estimate.
- Put detail behind @imports (@docs/style.md etc.), never inline.
- Include: Project one-liner, Response style (terse), Commands, Guardrails.
- Do NOT restate anything the agent can trivially infer from the tree.

Write the result to ./CLAUDE.md and print the token estimate.

Wire regeneration into CI so the file never drifts or bloats:

# .github/workflows/claude-md.yml
name: Regenerate CLAUDE.md
on:
  push:
    paths: ["package.json","pyproject.toml","go.mod","Cargo.toml"]
jobs:
  regen:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Regenerate lean CLAUDE.md
        run: claude -p "/gen-claude-md" --dangerously-skip-permissions
      - name: Commit if changed
        run: |
          git config user.name  "claude-bot"
          git config user.email "bot@example.com"
          git add CLAUDE.md
          git diff --cached --quiet || git commit -m "chore: regenerate lean CLAUDE.md"
          git push

6.4 Skill / command scaffolding from repeated patterns

When you notice the same multi-line instruction typed twice, scaffold it into a command. This generator does it for you:

#!/usr/bin/env bash
# .claude/scaffold_command.sh NAME "one-line description"
# Creates a new slash command from a template.
set -euo pipefail
name="${1:?usage: scaffold_command.sh NAME \"description\"}"; desc="${2:-}"
f=".claude/commands/${name}.md"
[[ -e "$f" ]] && { echo "exists: $f"; exit 0; }
cat > "$f" <<MD
# /$name
$desc

Instructions:
- (fill in the exact prompt this command should run)
- Use \$ARGUMENTS for any parameters passed after the command.
MD
echo "created $f"

To shed MCP context cost, convert a hot MCP tool into a local command that calls the underlying API directly — you keep the capability without paying the per-turn schema tax on every session.

Part 7 — Rolling It Out to a Team

A playbook that lives in one engineer's head isn't a playbook — it's a hobby. Rollout is what turns it into an organizational default. The sequencing principle mirrors the framework itself: land the automatic wins first, build the habits second, and only then push the workflow discipline that needs the most buy-in. Trying to sell spec-driven development to a skeptical team on day one fails; showing them a 40% bill drop from a config change they didn't have to think about earns the credibility to go further.

7.1 Phase 1 — Pilot & baseline (Week 1–2)

Pick one high-traffic repo and one willing team. Don't boil the ocean.

  • Run the bootstrap installer (Part 6) on the pilot repo.
  • Measure first. Capture the current spend-per-developer and tokens-per-session before changing anything — you can't prove a win you didn't baseline.
  • Turn on governance only: routing, budgets, .claudeignore, lean CLAUDE.md. No habit asks yet.

7.2 Phase 2 — Prove it, then propagate (Week 3–4)

  • Compare spend against the baseline. A tuned routing + caching + CLAUDE.md-diet config typically lands a 40–60% drop with zero developer behavior change.
  • Publish the number. One Slack post — "same output, 47% lower bill" — does more for adoption than any mandate.
  • Roll the governance config to every repo via the installer in CI. This is a platform change, not a per-team negotiation.

7.3 Phase 3 — Train the habits (Month 2)

Now that the floor is raised automatically, introduce the Tier 2 habits — the part that needs humans:

  • Ship the standard slash-command pack to every repo.
  • Run one 30-minute brown-bag: /clear, Plan Mode, /cheap, /scope. Show, don't tell.
  • Stand up a shared cost dashboard (per-team, per-repo attribution) so the savings stay visible and teams see their own trend.

7.4 Phase 4 — Workflow discipline where it pays (Month 3+)

  • Introduce spec-driven development for production, shared-codebase, and compliance work — not everywhere (respect the Part 4 decision matrix).
  • Scaffold the spec commands into repos so they're one keystroke away.
  • Move toward self-configuring repos: new projects inherit the whole playbook on git clone, and the CLAUDE.md generator keeps context lean automatically.

7.5 Make it stick

  • A named owner. Someone owns the .claude/ config and the dashboard, or it rots.
  • Onboard through the repo, not a wiki. The playbook is code that ships with the project; a new hire inherits it by cloning, not by reading docs.
  • Review quarterly. Model prices, tiers, and tooling shift fast (they did four times in 2026 alone) — revisit the routing policy and caching config each quarter.

The takeaway

A smart developer isn't the one who remembers to be frugal. It's the one who builds a system where frugality is automatic — governance that enforces itself, habits that become muscle memory, a workflow that gets it right the first time, and a repo that configures itself on clone.

The token bill stops being a mystery and becomes a design parameter — and rolling it out is just sequencing: land the automatic wins, build the habits, then earn the workflow discipline. That's the whole game.

Governance catches 60%. Habits refine 40%. Automation ships 65% of it as code. The developer's job is the judgment that's left.
