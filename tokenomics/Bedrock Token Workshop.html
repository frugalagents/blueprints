The Bedrock Token Workshop

A half-day, hands-on workshop that follows the same path any real adoption follows: install and connect first, use what already ships built-in second, then customize — cheapest and simplest customization before the most powerful and most expensive. Every exercise is globally numbered (Exercise 1 through 29) so you can always say exactly where you are. Each exercise is a short "why," a numbered list of actions with a bolded → Expect: outcome you check after each one, and — where a real number or mechanism applies — a short cost-impact line.

Before you begin. You need a terminal and Claude Code installed. If you've never used a terminal, that's fine — every command below is written out in full. Install with: curl -fsSL https://claude.ai/install.sh | bash (macOS/Linux) or irm https://claude.ai/install.ps1 | iex (Windows PowerShell).
The shape of this workshop. Tabs 1–3 involve writing zero custom files — install, connect, and learn what's already built in. Tabs 4–7 are four increasing tiers of customization: plain text, then invokable procedures, then real scripting, then external integrations. Tab 8 is judgment — when to reach for which tool. Tab 9 is the recap and a linear day-one runbook. Every command, config snippet, and recommendation is drawn from Claude Code's own official documentation; look for the small italic Source line under explanatory blocks.

1 · Foundations & Economics

Everything in this workshop is a technique for managing one resource: the context Claude Code sends to the model on every request, and the tokens that context costs. This tab builds the mental model, in plain language, then proves it with a real number you'll watch move.

What Claude Code actually is

Claude Code is not a chatbot. A chatbot answers a question and waits. Claude Code is agentic: you describe an outcome, and it reads files, runs commands, writes code, and works through multi-step problems on its own.

It's also metered: every word it reads, every file it opens, every line it writes back costs a small amount of money. The cost isn't in what Claude produces — it's in what it has to read and re-read to produce it. A one-line answer at the end of a long, messy exploration can cost 100x more than the same answer given with the right context already in place.

Source: Claude Code docs — Best Practices, opening section.

The harness: what sits between you and the model

The underlying model has no memory of its own — each call starts from zero. Claude Code is the program that decides what gets handed to it — the "harness." Every message, it assembles a package: your standing instructions (CLAUDE.md), every tool description, the full conversation so far, and every prior file read or command result. It sends that package, gets a response, and if a tool runs, the result is added to the package for the next request.

The package never shrinks on its own — it only grows. This is why a session starts cheap and gets expensive fast.

Source: Claude Code docs — Best Practices, "Most best practices are based on one constraint"; Manage Costs, "Why usage climbs in a long session."

1See it for yourself — the five-line proof

You'll run the identical instruction twice — once with no standing instructions, once with a five-line CLAUDE.md. The only variable is that file. Whatever the cost difference is, that file caused it.

  1. Create an empty folder. Add 3–4 small text files, and inside them type a made-up function name — the same name — at least 5 times total, spread across at least 3 files (e.g. calculateTotal). → Expect: running grep -rn calculateTotal . prints at least 5 matches across 3+ files.
  2. In that folder, run claude, then /clear, then this exact prompt: 
    Rename calculateTotal to computeTotal everywhere in this folder, then check for anything that would now fail to compile or lint.
    Wait for it to finish. → Expect: it reports the rename done.
  3. Run /usage and write down the total tokens and dollar cost as "Run 1." → Expect: a real number, not zero.
  4. /clear, then create CLAUDE.md in the same folder with exactly: 
    # Project
Rename/search tasks: use grep/rg to find all occurrences before editing — never open every file to scan by eye.

# Response style
Be terse. Show a summary of files changed, not full diffs, unless asked.
    → Expect: running /context shows CLAUDE.md listed under Memory files.
  5. Give the identical prompt from step 2, word for word. → Expect: it finishes, using grep/rg instead of opening files one by one.
  6. Run /usage again and compare to "Run 1." → Expect: the new number is noticeably lower.
Cost impact: you just measured, in real dollars, the effect of five lines of standing instruction. Every tab from here on is this same lever, generalized and made permanent.

2 · Bedrock Setup & Routing Amazon Bedrock

Pure setup — no customization yet. By the end of this tab, Claude Code talks to Amazon Bedrock, with model versions pinned deliberately instead of left to drift.

2Confirm Claude Code is installed

Rule out an install problem before troubleshooting anything AWS-specific.

  1. Run claude --version. → Expect: a version number followed by (Claude Code). If "command not found," run the install command from the top of this page first.
3Enable Anthropic model access in the Bedrock console

AWS requires every account to explicitly request access to a model family — a one-time form, not a purchase or a waiting period.

  1. Open the Amazon Bedrock console → Model catalog → select Claude Sonnet 4.6 (and Opus/Haiku if you want all three tiers, recommended since later tabs use more than one) → submit the use-case access form. → Expect: the Model catalog immediately shows access as granted for each model — no approval delay.
4Attach the IAM permissions

The identity you authenticate as needs exactly the permissions to call models — no more, no less.

  1. In IAM, attach this policy to your role or user: 
    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowModelAndInferenceProfileAccess",
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream",
        "bedrock:ListInferenceProfiles",
        "bedrock:GetInferenceProfile"
      ],
      "Resource": [
        "arn:aws:bedrock:*:*:inference-profile/*",
        "arn:aws:bedrock:*:*:application-inference-profile/*",
        "arn:aws:bedrock:*:*:foundation-model/*"
      ]
    },
    {
      "Sid": "AllowMarketplaceSubscription",
      "Effect": "Allow",
      "Action": ["aws-marketplace:ViewSubscriptions", "aws-marketplace:Subscribe"],
      "Resource": "*",
      "Condition": { "StringEquals": { "aws:CalledViaLast": "bedrock.amazonaws.com" } }
    }
  ]
}
  2. Run aws bedrock list-inference-profiles --region us-east-1. → Expect: a JSON list, not an AccessDenied error. If it names a specific missing permission, add exactly that and re-run.
5Get AWS credentials into your terminal

Claude Code uses the same standard AWS credential chain as every AWS CLI tool — no separate login system.

  1. Pick exactly one: aws configure (named profile) · aws sso login --profile=your-profile-name then export AWS_PROFILE=your-profile-name (SSO) · export AWS_BEARER_TOKEN_BEDROCK=your-key (Bedrock API key, simplest, no AWS CLI needed).
  2. If you used a profile or SSO, run aws sts get-caller-identity. → Expect: your AWS account ID and ARN print back, not an error. (Skip this check for the API-key option — Exercise 6 verifies that path instead.)
6Point Claude Code at Bedrock

Switch the provider from the default to Amazon Bedrock using the credentials from Exercise 5.

  1. Run claude. At the first login prompt, choose 3rd-party platform → Amazon Bedrock. Already signed in elsewhere? Run /setup-bedrock inside a session instead — same wizard.
  2. Once at a normal chat prompt, run /status. → Expect: it says Amazon Bedrock as the provider, with a resolved AWS region. If not, repeat step 1.
7Pin your model versions

Without pinning, the "sonnet"/"opus" shorthand resolves to whatever the current default is — and that can silently move to a newer, pricier model.

  1. If the Exercise 6 wizard already offered to pin models and you accepted, skip to step 2. Otherwise, before starting claude: 
    export ANTHROPIC_DEFAULT_SONNET_MODEL='us.anthropic.claude-sonnet-4-6'
export ANTHROPIC_DEFAULT_HAIKU_MODEL='us.anthropic.claude-haiku-4-5-20251001-v1:0'
    Match the prefix to your region: us. for us-*, eu. for eu-*, apac. for ap-*, global. otherwise.
  2. Run /status again. → Expect: it lists the exact full model ID you set, not a bare word like sonnet.
Cost impact: an unpinned deployment that silently upgrades from Sonnet-tier to Opus-tier is a real, documented failure mode — Opus costs meaningfully more per token. Pinning costs nothing and prevents an invisible, un-budgeted increase.
8Switch model tier mid-session

There is no automatic "this is simple, use a cheaper model" feature. The only manual, whole-session control is /model. Sonnet handles most coding work well and costs less than Opus; reserve Opus for genuinely hard architectural or multi-step reasoning.

  1. Run /model and select a different tier than your current default (e.g. Haiku if you're on Sonnet). → Expect: the status line reflects the new model.
  2. Ask a trivial one-word-answer question. → Expect: the reply returns noticeably faster than on the previous tier — the cheaper model is actually doing the work.

9Test-drive the panel, one command at a time

Type every cost-relevant command at least once now, so none of them are unfamiliar the first time you need one under pressure.

  1. In any real repo, run /status, then /context, then /usage. → Expect: you can describe, in one sentence each, what each screen showed.
  2. Run /model and actually pick an option (don't press Escape). → Expect: a confirmation of the new model.
  3. Run /effort and pick a level. → Expect: a confirmation of the new effort level.
  4. Run /hooks. → Expect: it plainly reports no hooks configured yet (you'll add real ones in Tab 6) — remember what "empty" looks like so you notice when it isn't, later.
  5. Run /doctor. → Expect: a clean report. Read it fully, even the fine parts — this is your baseline for "healthy."

10Set your personal defaults through /config

/config writes settings for you — no hand-edited JSON needed for a simple default.

  1. Run /config with no arguments and browse the menu without changing anything. → Expect: you can find the model and output-style settings.
  2. Run /config model=sonnet. → Expect: a confirmation it was set.
  3. Open a brand-new terminal, run claude, then /status. → Expect: the new session starts on the model you set — without running /model again.
Cost impact: a default set once removes an entire category of "I forgot to check which model I was on" waste, for every future session on this machine.

4 · Level 1 — Text & Declarative Config

1Plain English + flat JSON.No logic, no scripting — the simplest tier of customization there is.

CLAUDE.md and permissions rules are both just text you write once. This tab produces a real, runnable project and a real CLAUDE.md for it — not a hypothetical.

What belongs in CLAUDE.md, and what doesn't

CLAUDE.md is read at the start of every conversation — billed every turn, no exceptions. The test: for every line, ask "would removing this cause a mistake?" If no, delete it.

✅ Include❌ Exclude
Bash commands Claude can't guessAnything Claude can figure out from your code
Code style rules that differ from defaultsStandard language conventions Claude already knows
Testing instructions, preferred test runnersDetailed API docs — link instead
Repository etiquette (branches, PRs)Information that changes frequently
Non-obvious gotchasSelf-evident advice like "write clean code"

Target: under 200 lines. Longer reliably degrades adherence, not just cost.

Source: Claude Code docs — Best Practices, "Write an effective CLAUDE.md."
11Build a real scratch project and a real CLAUDE.md for it

Every command in the CLAUDE.md below is real and actually runs against this tiny, dependency-free Node.js project. Check node --version first (18+ works); no Node? Ask your facilitator for an equivalent — the lesson transfers.

  1. Create a folder, then mkdir -p src tests. Create package.json: 
    {
  "name": "claude-md-demo",
  "version": "1.0.0",
  "type": "module",
  "scripts": { "test": "node --test", "lint": "node --check src/math.js" }
}
    Create src/math.js: 
    export function calculateTotal(items) {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}
    Create tests/math.test.js: 
    import { test } from 'node:test';
import assert from 'node:assert';
import { calculateTotal } from '../src/math.js';

test('calculateTotal sums price * quantity', () => {
  const items = [{ price: 10, quantity: 2 }, { price: 5, quantity: 3 }];
  assert.strictEqual(calculateTotal(items), 35);
});
    Run npm test. → Expect: 1 test passes. Fix the files before continuing if it doesn't.
  2. In the same folder, create CLAUDE.md: 
    # Project
Tiny Node.js demo package. Source in src/, tests in tests/. No external
dependencies — uses Node's built-in test runner.

# Commands
- Run tests: npm test
- Check syntax (our "lint" until we add a real linter): npm run lint

# Code style
- Use ES modules (import/export), not CommonJS (require)
- One exported function per file

# Workflow
- After changing any function in src/, run npm test and confirm it passes
  before saying the task is done
- Use rg or grep to find every call site of a function before renaming it —
  never open files one at a time to scan by eye

# Gotchas
- calculateTotal expects an array of {price, quantity} objects — it does
  not accept a flat array of numbers
    Start claude, run /context. → Expect: CLAUDE.md appears under Memory files with a token count — that's the fixed tax it now adds every turn.
  3. Ask: "Add a function applyDiscount(total, percent) to src/math.js that reduces a total by a percentage. Export it, add a test for it, and follow our workflow rules." → Expect: Claude runs npm test on its own before declaring done, without being told to this time.
  4. Run npm test yourself, independently. → Expect: 2 passing tests, not 1. Then delete the Workflow section, /clear, and ask for one more similar function. → Expect: notice whether it still runs tests unprompted — the contrast proves the earlier behavior came from the file, not instinct.
Cost impact: a file under 200 focused lines costs a small, fixed amount per turn and improves reliability. The workflow rule you watched fire prevents an entire category of expensive rework — without it, a broken implementation ships, you notice later, and correcting it re-bills the whole conversation a second time.
12Deny access to sensitive files

CLAUDE.md is advisory — Claude tries to follow it, no guarantee. permissions rules in .claude/settings.json are enforced by the program itself, before Claude can act, regardless of what the model decides.

  1. In your scratch repo: mkdir secrets && echo "fake-api-key=123" > secrets/keys.txt.
  2. Create or edit .claude/settings.json: 
    {
  "permissions": {
    "deny": ["Read(./secrets/**)"]
  }
}
    Ask: "What's in secrets/keys.txt?" → Expect: Claude reports it cannot read the file.
  3. Remove the deny rule, ask the exact same question again. → Expect: it can now read the file — the back-to-back contrast proves the rule, not the model's judgment, was blocking it. Put the rule back before moving on.
Cost impact: primarily risk-elimination, not cost-saving — but an accidental read of a large secrets dump or log file is exactly the kind of one-time event that spikes a session's token usage unpredictably. Denying the path removes that risk for every session, forever.
13Let a built-in checkup catch drift automatically

Files that are useful when written tend to grow as people add "just one more rule." /doctor flags content Claude could already infer, while leaving non-obvious rules alone.

  1. Open your CLAUDE.md from Exercise 11 and add a few lines that just restate the obvious — e.g. your package.json's dependency list, typed out by hand.
  2. Run /doctor. → Expect: it names the padding you just added as safe to remove, and leaves your original non-obvious rules alone. Accept the suggestion and remove the padding.
Cost impact: run this monthly (or in CI), and a file that would otherwise silently grow past the 200-line danger zone gets caught before it costs real money or reliability.

5 · Level 2 — Skills & Subagents

2Named, invokable procedures.Still just files with frontmatter — no shell scripting — but now they load only on demand instead of every turn.

A skill is a procedure Claude loads only when it's actually relevant. A subagent is a whole separate Claude Code instance, with its own tools and its own model, that you delegate a task to.

14Move an occasional procedure out of CLAUDE.md into a skill

If a procedure only matters for one kind of task, putting it in CLAUDE.md means it's billed every turn even on days nobody does that task. A skill (.claude/skills/<name>/SKILL.md) loads only when invoked.

  1. Create .claude/skills/api-endpoint/SKILL.md: 
    ---
name: api-endpoint
description: Steps for adding a new REST API endpoint in this project
---
# Adding a new API endpoint
1. Add the route in src/routes/
2. Add the handler in src/handlers/
3. Add an integration test in tests/api/
4. Update the OpenAPI spec in docs/openapi.yaml
  2. Start a fresh session, run /context. → Expect: the skill's content does not appear anywhere — invisible until you ask Claude to add an API endpoint, or type /api-endpoint directly.
Cost impact: every procedure correctly moved out of CLAUDE.md and into a skill is tokens that stop being billed on days nobody needs that procedure.
15Permanently pin a cheap model to a recurring simple task

A subagent's own file can pin its model, independent of whatever your main session is running — guaranteeing the cheap tier without anyone remembering to run /model by hand.

  1. Create .claude/agents/quick-reviewer.md: 
    ---
name: quick-reviewer
description: Reviews the current diff for critical/major issues only. Use after non-trivial edits.
tools: Read, Grep, Glob
model: haiku
---

You review diffs. Report only Critical and Major issues. Be terse.
  2. Make a small, deliberately flawed edit to any file (e.g. remove a null check). Ask: "Use the quick-reviewer agent to review my latest change." → Expect: the transcript shows a delegation line like quick-reviewer (Review latest change).
  3. Run /usage. → Expect: this review's tokens are billed at Haiku's rate, regardless of your main session's model.
Cost impact: any task your team does repeatedly and knows is low-complexity — reviews, lint fixes, commit messages — is a candidate for this exact pattern. Written once, it guarantees the cheap tier forever, for every teammate, with zero ongoing discipline.
16Build a subagent whose entire purpose is cutting context and cost

A subagent runs in its own, separate context window — it can read dozens of files, and only its summary returns to your main conversation. This one is read-only (can't rack up cost by editing) and pinned to Haiku.

  1. Create .claude/agents/codebase-researcher.md: 
    ---
name: codebase-researcher
description: Investigates how something works across the codebase — reads
  many files to answer a question — without polluting the main conversation.
tools: Read, Grep, Glob
model: haiku
---

You are a research-only subagent. You investigate and report; you never edit files.

Rules for keeping your report cheap to read:
- Do not paste full file contents back. Quote at most 3-5 line snippets,
  with a file path and line number, as evidence.
- Lead with a 2-4 sentence summary. Put supporting detail after.
- If you read more than 15 files and still don't have the answer, stop
  and report what you've ruled out.
- End with a short list of exact file paths relevant to the question.
    Run cat .claude/agents/codebase-researcher.md. → Expect: the frontmatter block between the --- markers saved exactly as written — a broken frontmatter block is the most common reason a subagent silently fails to register.
  2. In a real repo, ask: "Use the codebase-researcher agent to investigate how our authentication system handles token refresh, and whether we have any existing OAuth utilities I should reuse." (Substitute any real "how does X work across files" question if you have no auth system.) → Expect: the summary leads with 2-4 sentences, not a wall of pasted file content.
  3. Run /context. → Expect: the individual files the subagent read do not appear in your main session's breakdown — only the summary. Then run /usage. → Expect: the research billed at Haiku's rate, even if your main session is on Sonnet or Opus.
Cost impact: this file compounds two savings at once — isolation (research noise never touches your repeatedly-rebilled main conversation) and model tier (Haiku pricing regardless of your session's tier). Research/investigation tasks are the highest-leverage place to apply both together.

6 · Level 3 — Hooks & Automation

3Real scripting.Shell scripts that read JSON on stdin and return a decision — the first tier where a bug in your own code can break something.

Hooks are deterministic: the script decides, not the model. Unlike CLAUDE.md, which is advisory, a hook fires every time, with zero exceptions.

17Write an enforcement hook — block edits to a file, with zero exceptions

A PreToolUse hook can inspect a pending action and block it before it runs. Claude can even write this script for you if you describe it in plain English.

  1. Create .claude/hooks/protect-files.sh: 
    #!/bin/bash
INPUT=$(cat)
PATH_ARG=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
case "$PATH_ARG" in
  *".env"*)
    echo "Blocked: edits to $PATH_ARG are not allowed by policy." >&2
    exit 2
    ;;
esac
exit 0
    Run chmod +x .claude/hooks/protect-files.sh.
  2. Wire it into .claude/settings.json: 
    {
  "hooks": {
    "PreToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh" }] }
    ]
  }
}
  3. Create a dummy .env file. Ask: "Add a comment to the top of .env". → Expect: Claude's reply shows the exact text Blocked: edits to ...env are not allowed by policy.
  4. Open .env yourself. → Expect: completely unchanged — the edit was stopped before it happened, so no tokens were even spent generating the blocked content.
18Write a hook that directly cuts token cost

When Claude runs a test suite, the entire output — every passing test — is read into context and billed, even though only failures matter. A hook can rewrite the command itself to filter before it runs. This is Claude Code's own documented example for this exact problem.

  1. Run mkdir -p ~/.claude/hooks (user-level, so this applies to every project on your machine). Create ~/.claude/hooks/filter-test-output.sh: 
    #!/bin/bash
input=$(cat)
cmd=$(echo "$input" | jq -r '.tool_input.command')

if [[ "$cmd" =~ ^(npm test|pytest|go test) ]]; then
  filtered_cmd="$cmd 2>&1 | grep -A 5 -E '(FAIL|ERROR|error:)' | head -100"
  echo "{\"hookSpecificOutput\":{\"hookEventName\":\"PreToolUse\",\"permissionDecision\":\"allow\",\"updatedInput\":{\"command\":\"$filtered_cmd\"}}}"
else
  echo "{}"
fi
    Run chmod +x ~/.claude/hooks/filter-test-output.sh.
  2. Wire it into ~/.claude/settings.json: 
    {
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "~/.claude/hooks/filter-test-output.sh" }] }
    ]
  }
}
  3. In the Exercise 11 project (or any repo with a working test command), run claude --debug and ask: "Run the test suite." → Expect: the debug log shows modified tool input keys: [command] — the hook rewrote the command before it ran. /hooks lists filter-test-output.sh under PreToolUse.
  4. Run the same test command yourself, unfiltered, in your own terminal. → Expect: for a real project with hundreds of tests, the unfiltered version runs tens of thousands of tokens while the filtered version Claude actually processed is a few hundred — Claude still got an accurate pass/fail signal.
Cost impact: the single biggest lever in Claude Code's "reduce token usage" guidance — offload filtering to a cheap script instead of paying the model to read-and-ignore noise. Any repeated, noisy command (test suites, build logs, linters) is a candidate.
19Match reasoning depth to the task

Reasoning tokens are billed as output. The default reasoning budget can run into the tens of thousands of tokens per request on some models. Lower effort on a genuinely simple task is close to pure savings.

  1. Run /effort and choose low. Ask a trivial one-line question. → Expect: the reply returns noticeably faster than at the default level.
  2. Run /effort again and set it back to high. → Expect: confirmed — don't leave a team session running at reduced effort by accident for tasks that need it.

7 · Level 4 — MCP Servers & Plugins

4External integrations.The most powerful and most expensive tier — a standing cost on every session from the moment you connect, whether or not that session ever uses it.

MCP servers connect Claude Code to systems outside your codebase. Plugins bundle skills, hooks, subagents, and MCP servers together into one install. Treat both as "mandatory only."

20Audit what's already connected

Before connecting anything new, know what's already there and whether you can justify each one.

  1. Run /mcp. → Expect: a list of connected servers (possibly zero — that's fine). For each one, you should be able to say, out loud, what task you use it for. If you can't, note it for removal.
21Connect, disable, and remove a real server

Practice the full lifecycle once on a real, low-risk server, so "disable what you're not using" is a habit you've actually performed.

  1. Run claude mcp add --transport http notion https://mcp.notion.com/mcp (no API key needed to add; OAuth happens on first use). Run claude mcp list. → Expect: notion appears with a status.
  2. Run /context, note what it reports for tool-related context. Run /mcp, select notion, toggle it off. → Expect: /mcp now shows it disabled but still listed — configuration intact, cost gone.
  3. If you're fully done with it: claude mcp remove notion. → Expect: claude mcp list no longer shows it at all.
Cost impact: a connected-but-unused server is pure overhead with zero benefit. Disabling costs one command and is instantly reversible — there's never a reason to leave something connected "just in case."
22Apply the same "mandatory only" filter to plugins

A plugin can bundle several MCP servers, hooks, and skills at once — one install command can silently add a lot of standing cost if you don't check what's inside first.

  1. Run /plugin and browse the marketplace without installing anything yet. Pick one genuinely relevant to your work. → Expect: you can read what it bundles before deciding.
  2. Only proceed to install if you can name a specific, real task you'll use it for. If so, install via the on-screen instructions (typically /plugin install <name>@<marketplace>).
  3. Run /mcp and /hooks again. → Expect: you can name exactly what the plugin added to each list — no silent, unexplained entries.
Cost impact: plugins are the highest-leverage place for accidental bloat, precisely because one install adds several things at once. Apply the "can I name what this does and why I need it" test before installing, not after noticing context is heavier than expected.

8 · Habits & Workflow

Every tool from Tabs 3–7 now exists. This tab is judgment — when and why to reach for which one, in the moment, inside a live session or across a whole feature.

Part A — Habits: the five documented failure patterns

23Diagnose a real session, then apply the matching fix

Catch yourself live, mid-bleed, with a real diagnostic command — not in the abstract.

  1. In a real repo, deliberately create a kitchen-sink session: ask about three unrelated parts of the codebase back to back, without clearing between them.
  2. Run /context. → Expect: you can identify the single largest category by token count. Write down which one it is.
  3. Run /clear, then /context again. → Expect: the conversation-history category is now at or near zero — not summarized, not hidden, actually gone from what's billed on your next message.
Cost impact: every message in a stale session re-bills the entire history before it, every time. This is the single highest-leverage habit in the workshop precisely because it's free, instant, and has zero downside when tasks are genuinely unrelated.
24Give Claude a way to check its own work

Without a check it can run, "looks done" is the only signal Claude has, and you become the entire verification loop. Give it a pass/fail and the loop closes on its own.

  1. Pick a small function in a real repo. Instead of "implement a function that validates email addresses," ask exactly: "write a validateEmail function. Example test cases: user@example.com is true, invalid is false, user@.com is false. Run the tests after implementing."
  2. Read the final message. → Expect: it shows the actual test output it ran, not just a claim of success. If it only asserts success, ask it directly to show the command and its result.
Cost impact: reviewing evidence Claude already gathered is cheaper than re-running verification yourself, and it means an unattended session can finish correctly instead of silently producing something wrong that costs another full correction round later.
25Course-correct within two tries, not five

Once you've corrected the same issue twice without success, context is polluted with failed approaches, which actively biases what comes next.

  1. In a real session, if you catch yourself correcting the same misunderstanding a third time, stop. Run /clear instead.
  2. Write one new prompt that states the task and explicitly names what you learned from the failed attempts. → Expect: the fresh, informed prompt resolves in fewer total turns than continuing to correct in place would have.
Cost impact: every failed correction re-bills the entire accumulated history of every previous attempt — a correction loop gets more expensive per attempt, not cheaper, the longer it runs.

Part B — Workflow: getting it right on the first attempt

Governance and habits make each turn cheaper. Workflow makes the whole task cheaper by avoiding rework. Rule of thumb: if you could describe the diff in one sentence, skip the plan.

26Decide whether this task needs a plan at all

Planning has real overhead — don't pay it for a typo fix, and don't skip it for a multi-file change you're unsure about.

  1. Pick a task you actually need done. Try to describe the resulting change in exactly one sentence. → Expect: if you succeed, skip to doing it directly — no plan needed. If the sentence needs "and"/"then" more than once, continue to Exercise 27.
27Explore, then plan — before any code is written

Plan Mode lets Claude read and answer questions but not edit anything, so it doesn't jump to code that solves the wrong problem.

  1. Press Shift+Tab repeatedly until the status bar shows plan mode on.
  2. Ask an exploration question first: "Read the relevant part of the codebase for [your feature] and explain how it currently works." Then: "Based on that, create a detailed plan. What files need to change?"
  3. Run git status. → Expect: no changes — Plan Mode cannot edit. Read the plan itself; → Expect: specific files and a specific approach, not vague generalities.
28Implement against the plan, then commit

A plan costs a few hundred tokens to produce and review. An implementation built on a wrong assumption costs the wasted work, the diagnosis, and the redo. Rework — not exploration — is the most expensive thing an agent does.

  1. Press Shift+Tab to leave Plan Mode (or approve the plan). Ask: "Implement the plan. Write tests, run the test suite, and fix any failures." Then: "Commit with a descriptive message and open a PR."
  2. Run git log --oneline -1. → Expect: a commit with a message that actually describes the change. Run your project's real test command yourself, independently. → Expect: it passes — don't take Claude's report as the only check.
29For a larger feature, let Claude interview you and produce a real spec

A spec is only as good as the questions that produced it. Rather than writing one yourself and hoping you thought of everything, have Claude interview you, then implement from the written result in a fresh, clean session.

  1. Pick a real feature bigger than a one-sentence diff — for example, "export dashboard data as CSV with rate limiting." Type: 
    I want to build a rate-limited CSV export feature. Interview me in detail using the AskUserQuestion tool.

Ask about technical implementation, UI/UX, edge cases, concerns, and tradeoffs. Don't ask obvious questions, dig into the hard parts I might not have considered.

Keep interviewing until we've covered everything, then write a complete spec to SPEC.md.
    Answer honestly, including "I hadn't thought about that" where true.
  2. Open SPEC.md. → Expect: something with this shape and this level of concreteness, not vague language: 
    ## requirements.md
US-1: Authenticated user exports current dashboard view as CSV
Given a user is authenticated and viewing a dashboard
When they click "Export CSV"
Then a CSV of the visible rows downloads, named <dashboard>-<date>.csv
And the user is rate-limited to 10 exports/hour/account

## tasks.md
- [ ] T1: Redis rate-limit middleware [parallel-safe]
- [ ] T2: Audit-log table migration [parallel-safe]
- [ ] T3: POST /export endpoint [depends: T1, T2]
- [ ] T4: Streaming CSV generator [parallel-safe]
- [ ] T5: Wire endpoint → generator [depends: T3, T4]
    Notice what a bare "add a CSV export button" prompt would have silently skipped: the rate limit, the streaming cap, the audit log.
  3. Run /clear, then ask Claude to implement exactly what's in SPEC.md.
  4. Run /context early in this new session. → Expect: the lengthy interview conversation is not present — only SPEC.md is being read. The implementation session starts clean and focused.
Cost impact: every ambiguity the interview resolves up front is one less round of "actually, I meant something different" mid-implementation — and each of those rounds re-bills everything that came before it.

9 · Checklist & New Project Playbook

Section A recaps every exercise, grouped by the same complexity tiers you climbed. Section B is the linear runbook: if you started a brand-new project tomorrow, do these in this order.

Section A — Recap Checklist

Setup (Exercises 2–8)

  • Claude Code installed and version confirmed (Ex. 2)
  • Model access enabled in Bedrock console + IAM policy attached (Ex. 3–4)
  • AWS credentials configured, Claude Code connected to Bedrock (Ex. 5–6)
  • Model versions pinned, not left on a bare alias (Ex. 7)
  • Comfortable switching tiers with /model mid-session (Ex. 8)

Built-in toolkit (Exercises 9–10)

  • Ran every cost-relevant slash command at least once and can read its output at a glance (Ex. 9)
  • Personal default model/effort set via /config (Ex. 10)

Level 1 — Text & config (Exercises 11–13)

  • A lean CLAUDE.md under 200 lines that changes real behavior (Ex. 11)
  • permissions.deny covering secrets/credentials (Ex. 12)
  • /doctor run and its trims accepted (Ex. 13)

Level 2 — Skills & subagents (Exercises 14–16)

  • At least one occasional procedure moved into a skill (Ex. 14)
  • A cheap-tier subagent pinned to a recurring simple task (Ex. 15)
  • A read-only research subagent that isolates noisy investigation (Ex. 16)

Level 3 — Hooks (Exercises 17–19)

  • An enforcement hook protecting at least one sensitive path (Ex. 17)
  • A cost-reduction hook filtering noisy command output (Ex. 18)
  • /effort matched to task difficulty, not left at default for everything (Ex. 19)

Level 4 — MCP & plugins (Exercises 20–22)

  • Every connected MCP server has a named, justified use (Ex. 20)
  • Know the add → disable → remove lifecycle by hand, not just in theory (Ex. 21)
  • Every installed plugin passes the "can I name what it does" test (Ex. 22)

Habits & workflow (Exercises 23–29)

  • /clear the moment you switch to an unrelated task (Ex. 23)
  • Every non-trivial task given a way to verify itself (Ex. 24)
  • Course-correct within two tries, not five (Ex. 25)
  • One-sentence test applied before deciding to plan (Ex. 26)
  • Plan Mode used for any change you couldn't describe in one sentence (Ex. 27–28)
  • Interview-driven SPEC.md for any genuinely large feature (Ex. 29)

Section B — New Project Playbook

Starting a brand-new project tomorrow? Do these in this exact order — each one is the exercise that already taught you how.

  1. Install Claude Code and confirm the version. (Ex. 2)
  2. Enable model access in the Bedrock console for your account. (Ex. 3)
  3. Attach the IAM policy and verify with list-inference-profiles. (Ex. 4)
  4. Get AWS credentials into your terminal. (Ex. 5)
  5. Point Claude Code at Bedrock and confirm with /status. (Ex. 6)
  6. Pin your model versions before anyone else touches this project. (Ex. 7)
  7. Tour the built-in command panel once, cold, in the new repo. (Ex. 9)
  8. Run /init to generate a first-pass CLAUDE.md from the real codebase, then trim it with /doctor until it's under 200 lines and every line earns its place. (builds on Ex. 11 & 13)
  9. Write permissions.deny rules for every secret/credential path in this specific repo before anyone runs Claude Code against real data. (Ex. 12)
  10. Identify one or two occasional procedures this project will need repeatedly (a migration checklist, a release process) and write them as skills, not CLAUDE.md entries. (Ex. 14)
  11. Define a cheap-tier subagent for whatever this team's most common low-complexity task will be. (Ex. 15)
  12. Write the enforcement hook protecting your secrets paths, and the cost-reduction hook for this stack's test/build command. (Ex. 17–18)
  13. Connect only the MCP servers this project genuinely needs on day one — none "just in case." (Ex. 20–21)
  14. Commit .claude/settings.json (env, permissions, hooks) and every hook script to git — never commit credentials themselves. Confirm with git show --stat.
  15. Prove it: clone the repo into a brand-new, separate directory with zero personal setup, start claude, and confirm the same secrets path is still blocked with no configuration performed in that directory.
  16. Brief the team on the habits: /clear between tasks, Plan Mode before multi-file changes, and the one-sentence test for when a spec is worth writing. (Ex. 23, 26–29)
